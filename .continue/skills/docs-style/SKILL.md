# Docs スタイルガイド

## 原則

- **簡潔に** — 無駄な言葉を省く。探しているものを簡単に見つけられるようにする。
- **タスク指向** — 製品ができることではなく、ユーザーが何をしようとしているかに基づいて構成する。
- **段階的な開示 (Progressive disclosure)** — 導入から高度なユースケースへと導く。ユーザーをいきなり深い部分に放り込まない。
- **抽象的な説明よりも実例を** — 説明するのではなく、示す。
- **コードスニペットはコピー＆ペースト可能であること** — 静かに動作を壊すようなプレースホルダー値や、インポートの欠落を避ける。
- **前提条件を最初に** — 作業の途中でユーザーを驚かせない。
- **1ページにつき1トピック** — 2つのことを扱う場合は、ページを分ける。
- **繰り返さずリンクする** — コンテンツを重複させるのではなく、他のドキュメントを参照する。
- **スキャンしやすい見出し** — 目次をざっと見るだけでページの構造がわかるようにする。
- **期待される出力を示す** — ステップの後に、ユーザーが何を見るべきかを伝える。
- **一貫した用語** — コンセプトに対して1つの用語を選び、どこでもそれを使用する
- **主要な製品機能にはスクリーンショット/GIFを使用する** — テキストよりも視覚的な方が早く伝わる場合は、ビジュアルを使用する
- **書いているドキュメントの種類を理解する** — チュートリアル（学習）、ハウツー（タスクの完了）、リファレンス（調べもの）、または解説（理由の理解）。これらを1つのページで混ぜない。
- **チュートリアルは完了可能であること** — すべてのステップに従ったユーザーが、毎回動作する結果を得られるようにする。
- **リファレンスドキュメントは網羅的かつ一貫していること** — すべてをカバーし、すべてのエントリで同じ構造を使用する

## トーン

- **恩着せがましくない** — 読者は開発者である。「Xを使うべきかYを使うべきか」の比較表で、「いつ何を使うべきか」を教え込まない。区別が重要な場合は、該当セクションの冒頭で簡潔に述べ、すぐに本題に入る。
- **読者の時間を尊重する** — 何を見ようとしているかを説明する段落ではなく、コマンドやコードから始める。まず対象を示し、その後に説明する。
- **個性を出さない** — ドキュメントはキャラクターではない。温かみを出そうとしたり、巧妙に振る舞ったり、愛着を持たせようとしたりしない。「さあ、始めましょう！」、「〜の魔法」、「プロのヒント：」、見出しに絵文字を使う、などは避ける。開発者はそれを見抜いてしまい、ドキュメントの格好をしたマーケティングコピーのように感じてしまう。単に直接的で臨床的に。ドキュメントは情報を提供するものであり、読者と関係を築くものではない。
- **コールアウトボックスよりもインラインのガイダンス** — `<Tip>`, `<Info>`, `<Warning>` などのコンポーネントを使用するよりも、文章の中にヒントを織り込むことを好む。これらのコンポーネントは読書の流れを遮り、多用すると重苦しく見える。本当に重要な警告（例：データの損失、セキュリティ）のために取っておく。1ページにつき1つが目安であり、ゼロでも問題ないことが多い。
- **例はリアルであること** — 現実的なファイルパス、現実的なプロンプト、現実的なタスクを使用する。`> Tell me about the CLI` ではなく `> @tests/auth.test.ts This test started failing after the last migration` のようにする。
- **例には価値を持たせる** — コードブロックの中に英語のプロンプトを置いただけの「例：Xをする」セクションを追加しない。例は、非自明な構文、フラグ、パイピング、または設定を示す場合に価値がある。読者がページの他の部分から理解できるのであれば、例は省略する。
- **「次のステップ」セクションを作らない** — 他のページへの CardGroups へのリンクを含む「次のステップ」や「次にすること」セクションでページを終わらせない。サイドバーのナビゲーションがすでにその役割を果たしている。他のページへのリンクが関連する場合は、汎用的なフッターではなく、文脈がある場所にインラインで配置する。
- **ページタイトル = サイドバーのタイトル** — フロントマターの `title` はサイドバーのラベルと一致させる必要がある。正当な理由がない限り `sidebarTitle` は使わない。ページタイトルに余計なコンテキストを詰め込まない（例: "Continue CLI (cn) Overview" → "Overview"）。
- **フロントマターにサブタイトル/説明を含めない** — `description` フィールドを使用しない。ページの冒頭の段落で必要なコンテキストを提供すべきである。メタデータのサブタイトルは煩雑さを加え、文章ですでに述べている内容を重複させる。

## 見出し

- **直接的で平易に。巧妙さや惹きつけを狙わない** — 見出しは単にそのセクションの内容を示すものであるべきである。直接的なものであれば動詞を使用してもよい（例: "Resume previous sessions"）。動名詞句がチュートリアルの章タイトルのように聞こえるのは避ける（例: "Giving Context with @" → "`@` Context"）。テストすべきは文法ではなくトーンである。もし親しみやすいナレーターが案内しているように聞こえる場合は、書き直す。単にそのセクションが何をカバーしているかを平然と述べているのであれば、それでよい。
- **説明的であることよりもスキャンしやすさ** — 目次をざっと見るだけでページの構造がわかるようにする。見出しは短く平易に保つ。
